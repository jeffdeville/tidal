# Documentation Capture During Reassessment

When reassessing a directive (especially one where all tasks have completed), you have context that no other agent will ever have: the panel deliberation, the decomposition rationale, execution outcomes, and what was learned. **Capture this knowledge before your session ends.**

## When to Write Documentation

Write documentation during reassessment when ANY of these are true:

- All tasks completed successfully — the directive is done, capture what was learned
- Tasks failed and you restructured — document why the original plan was wrong
- You discovered something non-obvious about the codebase during analysis
- Domain CLAUDE.md files are missing for areas that were heavily modified

**Skip documentation** when:
- You're only retrying transient failures (flaky tests, timeout)
- The directive was trivial (single task, no interesting decisions)

## What to Document

### 1. Domain CLAUDE.md Files (Highest Value)

These live at `lib/<domain>/CLAUDE.md` and are the first thing future agents read when working in that domain.

**Update when**: The directive touched a domain and you learned something about it that isn't already captured.

**Format** — follow the existing pattern (see `lib/colony/execution/CLAUDE.md` as reference):
- Module responsibility table
- Key patterns and state machines
- Common mistakes section
- What NOT to do (anti-patterns discovered during execution)

**Create when**: A domain directory has no CLAUDE.md and the directive modified 3+ files in it.

### 2. Architecture Docs (`.colony/architecture/`)

**Update when**: The directive changed how components interact, added a new integration pattern, or modified an existing architectural contract.

**Create when**: A new architectural pattern was established that cuts across domains.

### 3. ADRs (`.colony/adr/`)

**Create when**: You made a significant structural decision during decomposition that future directives should know about. Use the format:
```
# ADR-NNN: Title

## Status: Accepted

## Context
[What situation led to this decision]

## Decision
[What we decided and why]

## Consequences
[What follows from this decision — both positive and negative]
```

Number sequentially from the highest existing ADR number.

### 4. Constraint Docs (`.colony/constraints/`)

**Update when**: Execution revealed a constraint that wasn't previously documented (e.g., "Arena processes can't access the DB in tests without explicit sandbox checkout").

## How to Commit Documentation

Since you're running in the main project repository, use this workflow:

```bash
# 1. Create a documentation branch
git checkout -b docs/directive-<short-directive-id>

# 2. Write your documentation files
# (use the Write/Edit tools as normal)

# 3. Stage only documentation files
git add lib/*/CLAUDE.md .colony/**/*.md

# 4. Commit with a clear message
git commit -m "docs: update knowledge base from directive <directive-id>

Captures learnings from: <directive title>
- <brief list of what was documented>"

# 5. Push and create a PR
git push -u origin docs/directive-<short-directive-id>

# 6. Create a PR (docs-only PRs can merge directly)
gh pr create --title "docs: <directive title> learnings" \
  --body "Documentation updates from directive execution. Auto-generated by Foreman reassessment."

# 7. Merge directly (docs don't need CI)
gh pr merge --squash

# 8. Return to the default branch
git checkout main
git pull origin main
```

**Important**: Only stage documentation files. Never include code changes in a documentation PR.

## What NOT to Document

- **Implementation details that are obvious from reading the code** — don't restate what functions do
- **Speculative future plans** — document what IS, not what might be
- **Per-task granular notes** — that's what PR descriptions are for. Domain docs should synthesize across tasks.
- **Anything that duplicates CQRS event data** — the event store already captures state transitions

## Quality Bar

A good CLAUDE.md update passes this test: "If a new agent started a task in this domain tomorrow, would this documentation save them from a mistake or help them understand something non-obvious?"

If the answer is no, don't write it.

## Relating Documentation to Existing Knowledge

Before writing, scan what already exists:
1. Read the domain's existing CLAUDE.md (if any)
2. Check `.colony/architecture/` for related architectural docs
3. Check `.colony/adr/` for related decisions
4. Don't duplicate — reference existing docs and extend them

Cross-reference when helpful:
```markdown
See also: [Three-Layer Model](/.colony/architecture/three-layer-model.md) for how this fits into Colony's overall architecture.
```
